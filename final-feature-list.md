# TradeFlow NG — Final Feature List

Date: 16 September 2026

Sources: requirements.md and screen-specification.md.

This is a five-day manual discovery experiment, with one manual service test only if discovery justifies it. It requires zero product screens and no software build. The ten Must-have FRs are grouped into six operational capabilities below; none is silently dropped or downgraded. Each description retains its source requirement references.

Must-have means necessary to run or evaluate the applicable experiment stage. Features 4–6 become applicable only after the Stage B entry gate passes. A check, introduction or coordination task is selected from evidence; these are not three services to build together. Customer pain, participant access and payer remain discovery questions.

No Could-have feature is justified by these files. None is added merely to fill the category. Optional use of an existing recording tool or a particular communication channel is not a separate product feature. WhatsApp, SMS and a separate field-agent interface are not prescribed capabilities; no channel integration is added.

## Five-day scope and what to cut first

The source has ten Must-have FR rows, retained here within six connected capabilities. Grouping reduces fragmentation, not the evidence or work required. Phone/direct communication and a manual log support all six rather than becoming separate software deliverables. All human validation and rejection/incomplete-information handling in screen-specification.md is included in features 1–6.

If capacity is insufficient, use this cut order:

1. Defer extra corroboration activity (CD-06) that does not resolve an essential task fact. This saves collection/visit effort while preserving clearly labelled customer accounts. Do not cut MT-02 checks required for the selected task.
2. Defer organizing optional supporting references (MT-06). Preserve core attributed notes, actions and outcomes; a dedicated document collection exercise is unnecessary.
3. If discovery has not established a feasible, timely test, defer Stage B as a whole (features 4–6) and complete discovery plus the recorded decision in features 1–3. Do not rush into an intervention to fit five days or report the service as validated.

If Stage B starts, do not selectively cut its baseline, permissions, essential checks, action history, follow-up or cost/economic-response records. If an outcome is unavailable by the end of the five-day window, record it as unknown rather than treating the test as proven successful. An unresolved payer blocks a commercial conclusion, not honest recording of the operational result.

The five-day limit is a team work window, not an invented transaction deadline, sample-size threshold or promise that discovery will validate a service. Customer facts determine the test deadline. A supported narrow/pause/reject decision is an acceptable experiment outcome.

Minimum product screens required: 0.
